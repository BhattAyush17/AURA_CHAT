# AURA — Agent Instructions

## Project

AURA is a voice-first AI companion. Real-time bidirectional voice via Gemini Live WebSocket, with a cognitive layer (longitudinal memory, behavioral routing, conversational music) wrapping the LLM. Frontend = Vite + React 19 + TanStack Router. Backend = FastAPI (Python 3.12). Memory = Supabase pgvector.

Deployment topology:

- Frontend → Vercel (SPA, see `vercel.json`)
- API → Render web service (uvicorn)
- Async consumer → Render worker (`python -m backend.bus.consumer`)
- Memory consolidation → Render cron (daily 02:00)

## Frontend Architecture

- **Single SPA, no SSR.** `vite.config.ts` explicitly bypasses TanStack Start SSR (`Lovable TanStack config wrapper` is disabled). Do not re-enable SSR — comments in `vite.config.ts:7-8` say this was done to remove SSR errors.
- **Router:** `@tanstack/router-plugin` generates `src/routeTree.gen.ts` from `src/routes/*`. Add a new route by creating `src/routes/<name>.tsx`; the Vite plugin regenerates the tree on dev start.
- **Path alias:** `@/*` → `src/*` (see `tsconfig.json`).
- **Vite split chunks** in `vite.config.ts` manually partitions vendor (react, tanstack, supabase, genai, framer-motion, lucide) — keep the matcher pattern when adding big deps.
- **ESLint** has several rules explicitly disabled: `@typescript-eslint/no-unused-vars`, `@typescript-eslint/no-explicit-any`, `react-hooks/exhaustive-deps`, `no-empty`, `no-control-regex`. Don't try to "fix" them — they reflect deliberate project policy. Prettier conflicts are reported as errors via `eslint-plugin-prettier`.
- **Tailwind v4** is configured via `@tailwindcss/vite` plugin only — there is no `tailwind.config.js`. Tokens live in `src/styles.css`.
- **`src/main.tsx`** exports `musicService`, `playbackState`, `buildMusicContext` on `window` for in-browser debugging. New top-level singletons that need console probing can follow this pattern.

## Backend Architecture

- **One FastAPI app** at `backend/api/main.py`. The repo-root `server.py` is just `from backend.api.main import app` so both `uvicorn server:app` and `uvicorn backend.api.main:app` work (Render uses the latter — see `render.yaml` and `Procfile`).
- **Cognitive pipeline** is split across `backend/core/` modules (behavior, emotion, sensing, response, frustration, withdrawal, vocab, relationship, pipeline). These are invoked synchronously per turn and feed directives into the Gemini system prompt.
- **Memory** is Supabase pgvector (`backend/memory/sync.py`, `chroma.py` is the legacy name — the file still exists but storage is pgvector, see `.agent_context/session_state.md`).
- **Async bus** = Redis Stream (`backend/bus/redis.py`); consumer entrypoint is `python -m backend.bus.consumer` (started as a separate Render worker).
- **Cron target** = `python -m backend.memory.consolidator --all --purge` (Render cron, daily 02:00 UTC).
- **CORS / origin check:** `ALLOWED_ORIGINS` env var in `backend/api/main.py:63`; includes `http://localhost:3000` and `:5173`. Add new dev origins there.
- **Supabase auth var:** use `SUPABASE_SERVICE_ROLE_KEY` (NOT `SUPABASE_SERVICE_KEY`) — backend falls back to `SUPABASE_KEY` if the role key is missing.
- **Redis:** backend reads `REDIS_URL` env var (Upstash `rediss://...` in `.env.local`). Default is `localhost:6379`. Failures are fail-open (degradation layer keeps the voice loop running).

## Verifying Changes

There is no CI and no formal test runner. Verification conventions:

- **Typecheck:** `npx tsc --noEmit` (frontend). `routeTree.gen.ts` is `@ts-nocheck`, ignore its noise.
- **Lint:** `npm run lint`. Expect Prettier complaints on new code; fix with `npm run format`.
- **Backend smoke:** `python test_demo_flow.py` and `python test_router.py` from repo root (against a running `server.py`). Full integration is run via `python test_runner.py`. These are gitignored.
- **Frontend integration:** ad-hoc `scripts/test-*.ts` scripts run with `tsx`; see `scripts/test-executive.ts`, `test-perception.ts`, `test-language.ts`, etc. Output is asserted in `docs/reports/phase-*.md`.
- **Voice pipeline** verification requires real audio devices — see `README.md` "Known Limitations".

## Gotchas That Will Bite You

1. **Route tree is generated.** Edits to `src/routeTree.gen.ts` are wiped on the next Vite dev start. Edit `src/routes/*` and restart.
2. **No SSR.** Don't add `getServerSideProps`, `loader()` server functions, or move routes into server-only paths. The whole frontend is client-side.
3. **`@/` alias works in Vite via `vite-tsconfig-paths` and in TS via `tsconfig.json`.** Keep both in sync if you change it.
4. **Google OAuth uses frontend popup Implicit Flow** (`src/auth/GoogleAuthProvider.ts`, `GoogleIdentityService.ts`). No `refresh_token` is or should be stored in the browser. This is intentional per `implementation_plan.md` Open Questions.
5. **Music is single-authority.** All playback routes through `src/music/MusicService` → `HTMLAudioPlaybackProvider`. The old `PlaybackEngine` / `PlayerStateMachine` were deleted (see README "Conversational Music"). Don't reintroduce parallel state.
6. **iOS audio session:** disabling `{ echoCancellation: false }` only works at the JS constraint level. iOS Safari can still force hardware "Communications Mode" — `README.md` documents this as an OS limitation, not a bug.
7. **Mobile autoplay:** programmatic `.play()` on iOS can be rejected. The pipeline preserves `pendingTrack` and surfaces a "Tap to enable music" affordance. Do not bypass `unlockAudio()` in new playback paths.
8. **Behavior-client speculative pre-fetch** (`src/lib/behavior-client.ts`): fires during user speech, debounced 500ms / 4-word minimum. Keep these thresholds when changing the client.
9. **Behavioral prompt is re-sent only on mode change / Euclidean distance >0.25 / 120s refresh.** Don't unconditionally re-inject on every turn — it destabilizes the LLM.
10. **Fail-open everywhere.** Redis/Supabase/embedding failures must not block the user-facing voice path. The `infrastructure/degradation.py` circuit breaker is the safety net.
11. **Test scripts are gitignored** (`scripts/`, `backend/tests/`, `backend/scripts/`, `test_*.py` at root, `legacy/`, `extracted_data/`, `chroma_behavior_db/`, `supabase_cli/`). Local-only — do not commit outputs.
12. **The `Lovable` reference** in `vite.config.ts:7` is historical. Lovable is not actively used; the file is the final form.
13. **TypeScript is `strict: true`** but `noUnusedLocals` / `noUnusedParameters` are off — dead imports are tolerated, unused parameters are tolerated. Don't enable them.
14. **Hinglish is a first-class language**, not a translation target. Both backend (`backend/personality/`) and frontend prompt building assume mixed-language turns.

## DevMemory — Project Code Memory

DevMemory is the local secondary code-memory and relationship index for this project.

Use DevMemory as a navigation and discovery aid when investigating:
- unfamiliar subsystems
- cross-file relationships
- architecture questions
- symbol ownership/dependencies
- debugging where the relevant code is not obvious
- tracing a flow across frontend/backend/modules

Before broad exploration, query DevMemory when it is likely to reduce search effort.

Available tools:
- `devmemory_devmemory-query` — search project memory
- `devmemory_devmemory-explain` — inspect a symbol and its relationships
- `devmemory_devmemory-neighbors` — inspect connected symbols/files
- `devmemory_devmemory-stats` — verify memory/index health

Use short, concrete queries first:
- symbol names
- subsystem names
- distinctive identifiers
- 2–5 word concepts

If a query returns nothing, retry with shorter or more identifier-focused terms before concluding that the project does not contain the concept.

IMPORTANT:
- DevMemory is a derived cache, NOT source of truth.
- Always verify important findings against the actual source files.
- Never implement a change solely from DevMemory output.
- Prefer actual source code over stale or ambiguous memory results.
- Use normal tools such as grep/rg, file reads, tests, and typechecking whenever they provide stronger evidence.
- Do not force DevMemory into every task; use it when it provides useful navigation or relationship context.

After substantial code changes, merges, pulls, or refactors, refresh the project memory:

`devmemory index`

If memory appears stale or inconsistent:

`devmemory stats`
`devmemory check`

If necessary:

`devmemory index --force`

Project source remains authoritative even when DevMemory disagrees with it.

### Retrieval preference

When using DevMemory, prefer this query order:

1. Exact symbol or class/function name
2. File/module name
3. Specific subsystem + identifier
4. Short technical phrase
5. Broad conceptual query only when necessary

DevMemory documentation results are leads, not implementation evidence.
When documentation appears in results, follow its references to the actual source code before making conclusions.

For implementation/debugging tasks, prioritize source-code nodes over documentation nodes.
Use `rg`/file reads to verify anything not directly established by source code.
